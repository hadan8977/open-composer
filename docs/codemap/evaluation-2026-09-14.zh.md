# 基于代码地图的评估：重构还是精简（2026-09-14）

作者：Fable 5.1。输入：`docs/codemap/codemap.json`（生成于 2026-09-14，提交 c632e61 的工作树，
含另一个执行代理正在写入的 Step 14 运行器文件）。数字都是生成时快照，重建地图后以新值为准。
目标：为个人使用提升质量、效率、性能，并让"产出与优化迭代策略"的速度上去。

## 0. 结论

**以精简为主，局部重构为辅，先精简后重构。** 不建议做整体重构。

- 代码库 25.5 万行 Python 里，40.7% 是按轮次命名的一次性研究模块，它们不在任何 cron 路径上，
  删除它们只波及 3 个源码文件。这类体量用"重构"去改抽象是浪费，用"精简"直接归档收益最大。
- 有三处必须做结构性修改而不是删除：研究包门面（性能）、8.7k 行的 `cli.py`（效率）、
  回测主路径上的迭代闸门（迭代速度）。这三处是"局部重构"。
- 内核、特征、数据、模拟盘四个节点是活跃且有测试的生产资产，不动它们的内部结构。

两点解读：

1. 体量集中在不跑的代码上。cron 每天真正执行的路径（数据归档、特征、观察周期）只有 2 万行，
   却要为门面链付 5 秒和 200 MB 的导入成本；每条 `oc` 命令同样如此。
2. 测试的一半以上在守护不会再跑的东西。轮次与路由两个节点的测试代码合计 4.3 万行，
   占测试代码的 54%，`make verify` 的时间大头在这里。

## 2. 为什么是精简优先

"重构"是在保留行为的前提下改变结构；"精简"是删掉不再需要的行为。地图显示的问题主要是后者：

- 一次性轮次模块每轮复制一份而非参数化（同一主题 14 个版本各 1.5k 到 3k 行），它们的结论已经
  写进 `reports/` 与进度日志，代码本身不再被产品路径引用。对它们做参数化重构没有收益，
  因为没有下一轮会复用这些具体实现，Step 14 通用运行器与 kernel 已是替代品。
- 精简后再看结构，剩余约 15 万行里真正需要改结构的只有三处（下一节），工作量可控。
- 反过来先重构会把大量精力花在即将删除的代码的导入、测试和门面适配上。

## 3. 三处必须的局部重构

| # | 位置 | 问题 | 改法 | 预期 |
|---|---|---|---|---|
| R1 | `open_composer/research/__init__.py` | 门面急切导入 42 个模块，任何 `import open_composer.research.x` 都触发，把 sklearn/LightGBM 拖进每次 CLI 和 cron | 清空门面，改为 PEP 562 `__getattr__` 惰性导出；同时把 `adapters/execution/adaptive_intraday_target_weights.py` 等对 research 的模块级导入改到函数内 | `oc --help` 从 5 s 降到 1 s 以内，cron 周期少加载约 200 MB；改完必须重测 |
| R2 | `open_composer/cli.py`（8,695 行，217 条命令） | 单文件承载全部命令与模块级导入，是导入成本和合并冲突的中心 | 先删轮次命令（精简 P0），再按命令组拆成 `open_composer/cli/<group>.py`，每个命令函数内惰性导入 | 命令数降到约 190，单文件消失，新增命令不再改巨型文件 |
| R3 | `engines/backtest_engine.py` 调用的 `require_iteration_execution_gate` | 回测主路径被治理闸门拦截，新想法要先写迭代档案才能跑一次回测 | 闸门只对 `strategy_specs/approved` 与 `active` 生效；`drafts` 直接可回测，报告标记 `workflow_pass` 而非研究通过 | 一个新 Spec 从写完到第一份回测报告不再需要治理产物 |

## 4. 分期方案

### P0 精简（预计 1 到 2 个执行代理工作日）

1. 归档节点"按轮次一次性研究模块"的 55 个文件与 41 个测试文件：移到 git 分支 `archive/rounds-2026-09`
   或仓库外，不保留在 import 路径。`reports/`、`prompts/`、`strategy_versions/` 里的历史产物原样保留。
2. 删除 cli.py 中 30 条对应子命令，修掉 `etf_structural_target_weights.py:23` 和
   `scripts/run_r7_forward_observation.py:6` 两处导入（后者随脚本一起归档）。
3. 用地图节点面板"下游影响"与"传递依赖它的测试"逐项核对，归档后跑 `uv run pytest` 与 `oc repo check`。

预期：Python 行减少约 41%，测试函数减少约 26%，命令 217 → 187。风险低，代码在 git 历史里。

### P0 性能（0.5 天）

R1 门面惰性化。验收：`uv run oc --help` 与 `import open_composer.research.kernel.loop` 均小于 1 秒，
cron 三条命令的 RSS 下降；用 `python -X importtime` 记录前后对比。

### P1 精简路由族（需要先决定保留哪些组合模式）

节点"路由与动量策略族"23,663 行、56 条只碰它的命令。`StrategySpec.portfolio.mode` 的九种模式里有五种
路由模式，这决定了哪些路由实现必须留下。建议：保留仍被 spec 模式和每日周期引用的
`beta_exposure`、`core_beta_satellite`、`model_ranking` 三条链，其余按 P0 的方式归档。
这一步需要用户确认要放弃的模式。

### P1 重构 cli.py（R2，1 天）

在 P0 与 P1 精简之后做，避免拆分即将删除的命令。

### P2 治理与 Dashboard

- 研究治理 18k 行中 cron 只用 469 行。保留 `gate_contract`、账本、知识索引、来源卡；
  campaign 合同与迭代档案改为"晋级到 approved 前必需"，研究阶段不再强制（AGENTS.md 在 Step 11 已豁免研究）。
- Dashboard 45 天零提交。个人使用下两种选择：冻结不动，或降级为 `oc dashboard html` 静态页并归档
  React 前端与历史 Vercel BFF。建议冻结，等策略层有产出再决定。

## 5. 对目标的预期收益

| 目标 | 来自哪一步 | 可验证的指标 |

## 6. 不做的事与需要用户决定的事

- 不动节点"研究内核""特征管线与因子库""数据适配""模拟盘、券商与安全控制"的内部结构，
  它们活跃、被引用、有测试。
- 不在精简的同时改门槛、改 StrategySpec 语义或改模拟盘安全逻辑。
- 需要用户决定：一次性模块是归档分支还是直接删除；路由族保留哪些组合模式；Dashboard 冻结还是降级。
