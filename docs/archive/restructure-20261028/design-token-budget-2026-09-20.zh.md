## 1. 2026-09-19 一整天的实测

| | 主会话（Opus / Fable） | 子代理（全部 Sonnet，6 个侦察 + 8 个执行） |
|---|---:|---:|
| 输入 | 48 | 2,146 |
| 输出 | 24,623 | 1,021,835 |
| 缓存写入 | 345,483 | 2,900,191 |
| **新鲜 token 小计**（输入 + 输出 + 缓存写入） | **370,154** | **3,924,172** |
| 缓存读取 | 7,835,246 | 149,285,094 |

三条直接读出来的事实：

1. **烧额度的是子代理，不是主会话**：新鲜消耗 392 万 vs 37 万，10.6 倍。预算控制点在"派几个、每个干多大的活"，不在"主会话少说两句"。
2. **缓存读取占 98%**。每一轮工具调用都把整个上下文重读一遍，单价虽是十分之一，量级在这里。它和"轮数 × 上下文大小"成正比，和输出多少几乎无关。
3. **最贵的不是产出多的任务，是轮数多的任务**。T2（删旧看板）253 次工具调用、29 万 token；T1（搬一个文件）111k token、90 次调用、**零产出**——全花在"起后台测试 + 轮询等结果"上。

单个子代理的成本画像（来自任务通知里的 `subagent_tokens`）：情报侦察 8–17 万；执行任务 10–29 万；给了地面真相（我先用 grep 查好文件清单、字段名、数量）的 T4/T5 是 ~120 次调用，没给的 T2 是 253 次。

## 2. 成本模型（够用的简化）

一次子代理任务的成本 ≈ Σ 每一轮（上下文大小 × 缓存读单价 + 新输入 + 输出）+ 首轮把简报和文件读进缓存的写入。

所以只有三个杠杆，按效果排序：

| 杠杆 | 作用在哪一项 | 可控程度 |
|---|---|---|
| **轮数**（工具调用次数） | 缓存读取 ∝ 轮数 | 高：简报越具体，探索越少 |
| **上下文大小** | 缓存读取 ∝ 大小；缓存写入 | 高：不 cat 大文件、不读整份计划、不回显输出 |
| **模型** | 所有项的单价 | 已定：Sonnet 执行，主会话判断 |

输出 token 是小项，"让它少写点"几乎不省钱。

## 3. 规则（从今天起执行）

**R1 简报里给足地面真相。** 我先用 grep / ls / 一段 python 把文件清单、字段名、数量、已知的坑查好写进简报，子代理不做探索。证据：T4/T5 vs T2，轮数减半。

**R2 验收命令只放秒级的。** ruff、`git grep`、单个测试模块、`oc repo check`。**全量 pytest 由主会话跑**，跑之前 `TaskStop` 掉执行者。证据：T1 的 111k 零产出。（已写进 [[route-subagents-to-sonnet-small-tasks]]。）

**R3 上下文瘦身。** 简报指明"只读计划的第 X 节"，不让它读整份文档；大文件用 `head` / `grep`，禁止 `cat`；产出文件不要在最终报告里回显；一个任务只碰一个模块。

**R4 复用还是新起。** 下一个任务和上一个碰的是同一批文件（≤5 个）且上一个执行者用量 <15 万时，用 `SendMessage` 续用同一个（省一次缓存写入）；否则新起一个（旧上下文已经太大，每轮重读更贵）。

**R5 并发上限 2，外加时间闸。** 执行任务超过 25 分钟且通知里没有提交，先看 `git status`，再决定 `TaskStop`。Agent 工具没有 token 上限参数，时间是唯一能提前介入的信号。

**R6 主会话也有上下文成本。** 主会话每一轮同样重读整个对话（今天主会话缓存读取 780 万，只有一个会话）。一个阶段（比如 Step 18 全部做完）结束后开新会话，比让上下文无限长便宜。

**R7 缓存读取不并入"总计"。** 界面和报告里，新鲜 token 是头条数字，缓存读取单列。把两者加成一个数会得到一个吓人且无意义的 1.5 亿。

## 4. 24 小时循环的预算闸（设计，待 24h 循环立项时实现）

前提：这台机器现在**读不到真实的订阅百分比**（长期 token 缺 `user:profile` 范围，交互登录的 token 已过期），Codex 是 API 计费没有订阅额度。所以闸门不能建在"剩余 %"上，只能建在**本地可测的新鲜 token** 和**被限流事件**上。

- **输入**：cockpit `/quota` 的滚动 5 小时窗新鲜 token（按角色、按任务）；会话记录里的 `quotaLimits{status: rejected, resetsAt}` 事件。
- **校准分母，不猜分母**：每次真的撞到 429，记下那一刻窗内的新鲜 token 数。几次之后这个数就是经验上的"窗口容量"，用它算百分比才是诚实的。cockpit 负责记录，不负责猜。
- **策略**：每个 5 小时窗给自主循环一个软上限（初始值 = 上次撞线量 × 60%，撞过线之前用保守常数），剩下的留给机主插话；估算超过软上限即暂停派单，等窗口滚动；读到 `rejected` 立即停，`resetsAt` 后恢复。
- **输出**：一个状态文件（循环读它决定要不要派下一单）+ cockpit 顶栏一行（`budget: 1.2M / 3.0M fresh, next reset 14:05`）。
- **单引擎**：Codex 没有第二套订阅额度，不假设它能分担；付费/免费 API 池只用于机械性、可丢弃的活。

## 6. 诚实的预期

不承诺百分比——分母还不知道。能承诺的是：T1 那种零产出的浪费归零；有地面真相的任务轮数从 250 降到 100 左右，缓存读取随之等比例下降；主会话按阶段开新会话。这三条加起来，同样的产出大约省一半；再往下就要靠 429 校准出真实容量之后按数字调。
