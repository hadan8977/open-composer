## 结论

你说得对：Codex 是在 Claude 之后接手的，你也针对这些问题改过好几轮，结果反而更慢。原因是这几轮优化改的都是规则文字，而拖慢它的是结构，结构恰恰是在这几轮调整里变的。

- **结构变了。** 10-13 起研究改成"常驻 owner + 常驻独立 peer"，会话一活就是 10 到 14 天，互相发消息、互相验收。最大的 9 个会话两周里被唤醒约 3,400 次，基本都是别的 agent 或进程事件触发的，你自己的消息只有 117 条。每次唤醒都要带着约 20 万 token 的上下文重读状态，平均一次约 230 万 token。
- **回执就是这么来的。** 有了常驻 peer，每次交接都要对方验收，验收又需要一个固定引用，于是出现了带 SHA 的回执。
- **规则改了，行为没改。** 你后面每一轮纠正都写进了规则：10-15 精简、10-16 取消自设的预算门、10-24 "先拿证据再建设施"。现在 AGENTS.md 已经明文禁止审批平台、轮询和逐份签署，但两周里还是有 2,131 条 agent 间消息，38% 带 SHA，约三分之一的工具调用花在处理回执和验收文件上。
- **纠正还变成了状态负担。** 每次纠正都成了控制文件里的新字段：owner-compute-hold.json 已经 187 KB，day-goal 86 KB，week-goal 76 KB，每次唤醒都要重读。

所以再改一次 prompt 也不会有用。要改的是结构本身：去掉常驻团队，也去掉 agent 之间的通信通道。

## 是模型问题还是设置问题

两者都有，以设置为主。

- **Codex 当主审时同样会缩小目标。** 10-09 到 10-12，Codex 先照搬了 Claude 的定时轮次结构。它自己在 10-11 做过对比：同样 6 小时，Claude 交付了 1 个带成本的结果，Codex 是 0，原因是主审把完整的研究目标缩成了"只做准备"和"申请审阅"。这只是一段 6 小时的样本，但和后来 Main 的方向偏离是一致的。
- **Codex 能干活，弱在判断。** 写代码、做实现没有问题，新的模拟盘服务和三个训练模型都是它做的。它弱在定范围和判断方向，而且倾向于把每条规则做成流程。10-10 加的"新方向、训练、转向前必须经独立 reviewer"，就被它套到了每一个变体上。

你问的"放弃得早"，三个因素都有：
- **退出机制：** 每个变体失败就封存。
- **迭代不深：** 没有在同一个机制上批量试变体。
- **模型倾向：** 容易停在安全边界就交接。

前两个属于设置，改结构就能解决。

## 方案

推荐方案 B：Opus 当主审，Codex 做一次性执行。其实就是恢复 Claude 时期验证过的结构，只把执行者从 Sonnet 换成 Codex。

- **主审：** Opus 5.5 max，每天 4 轮，每轮新开会话。每轮读新结果的原始数据，决定每个方向是继续迭代还是换方向，写 2 到 6 份自包含简报并派出，记一行台账，再给你发一条简报。
- **执行：** 每份简报起一个 `codex exec` 进程，做完就退出。简报写清楚命令、停止条件和固定的结果格式（`--output-schema`），并设超时。worker 之间没有通信通道，只写自己的目录。
- **审阅：** 主审自己复算关键数字，不再设常驻 peer。独立审阅只在两个节点做：新方向立项时一次，进模拟盘前一次，都用没有上下文的一次性 reviewer。这样仍然满足你 10-10 的规则。
- **方法：** 每个方向开一个开发期 campaign，在开发数据上批量试 20 到 50 个变体，记录试验次数并做 DSR 折扣。最好的那个做一次冻结的样本外评估，通过了就进模拟盘孵化。只有足够多真正不同的变体都失败、并且能说清机制为什么不成立，才停掉这个方向。已经冻结的研究和门槛都不动。
- **周目标：** 写成 2 到 3 个方向，加一个能数的产出，比如每个方向至少 30 个带成本的变体、至少 1 个模拟盘候选。现在的 week-goal 是 76 KB 的状态描述，检查时只能看出"偏没偏"，看不出"还差多少"。
- **额度：** 主审每轮读一次额度，按配速决定派几个 worker，比如每天不超过周额度的 15% 到 20%。每轮主审本身就是一次方向检查，比现在每涨 10% 检查一次更频繁，所以不再需要常驻额度经理和停机协议。

- **你看什么：** 一张台账，每轮一行：派出几个、拿回几个结论、花了多少 token、有几个模拟盘候选。

Claude 额度应该够用。Claude 时期主审轮本身 12 天只用了约 0.6B token，当时把额度用完的是 Sonnet 子代理和长时间的交互会话，这部分现在交给 Codex。我估计 Claude 用量会是当时日均的 1/8 到 1/4。内存方面，按现有预算同时跑 2 到 3 个 worker 可行。有一点实施时要先验证：worker 用 `run_capped` 放在独立的 systemd 单元里跑，确认主审轮结束后它不会被一起杀掉。

方案 A（纯 Codex）：结构完全一样，只是主审换成每轮新开的 Astra，并加两条约束：每份简报必须以一个带成本的数字收尾；主审不能创建常驻 agent，也不能新增控制字段。风险是方向判断仍然靠 Astra。适合在 Claude 额度用完时作为备用。

## pstack 评估

方法本身是对的，上次出问题的是用法：

- **原意：** 你 10-13 的要求是"纠正 agent 时，用测试、lint 把问题消掉，而不是加 prompt"。
- **实际落地：** "结构"被用在了合规上，加了 7 个门禁（预算锁、哈希绑定、准入证据等）、带哈希的交接脚本和更多状态文件。10-14 一次就新增约 3,700 行治理内容，角色配置从 10 KB 涨到 25 KB。
- **没有验证：** 当时准备的 8 个行为测试用例一个都没跑，所以没人发现改动反而让 agent 更慢了。

pstack 里适合这个项目、上次没用上的几样：
- **hillclimb：** 固定一个指标和测试框架，每行记一个假设，变好就保留，变差就回退，统一记在一张决策表里。进入平台期是换方法的信号，不是停的信号，正好对上"试几次就放弃"的问题。
- **autonomous-run：** 先写清楚做到什么程度才算完成。
- **每个任务开新 agent：** 只在少数情况下续用旧的，pstack 原文就是这么要求的。
- **少加多删：** 优先删除，改动越小越好。
- **结果复核：** 用一个没有上下文的新 reviewer 专挑结果的毛病，替代常驻 peer。
- **一张决策表：** 每个任务一张表，替代一堆 JSON 回执。

不适合的：PR、上线、TypeScript、界面这类软件工程 playbook。另外，pstack 默认是混用两家模型（判断用 Opus，写代码用快模型）；你要单厂商的话，就在同一家内部区分主审和执行。

这次的用法：结构指共享研究引擎、固定的结果格式、决策表，再加几个检查结果的脚本，比如自动发现策略里写死的开关。改完用 A/B 实测 agent 的表现，而不是只看文档有没有变短。

```
AGENTS.md          ≤6 KB：一段使命、硬规则、干活方式、去哪找东西
docs/rules.md      当前有效的机主规则，一页；历史移入 archive
docs/runbooks/     需要时再读：内存、Hadan、Modal、磁盘、模拟盘运维
control.json       只放开关：研究开/停、额度配速、各策略授权与到期
研究引擎（包内）   唯一的模拟器、成本、账本、指标/DSR、批量变体、试验台账
research/<方向>/   brief、固定格式的 results.json、decisions.tsv、少量代码
模拟盘生产         代码和配置进 git、移出研究目录，只能走 worktree 修改
board.md           每轮一行，你只看这个
archive/           全部历史，不删
```

开工前必读的内容控制在 30 KB 以内。agent 不能改治理文件，只能在报告里提建议。
