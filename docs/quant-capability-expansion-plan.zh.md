# Open Composer 能力补全与 Dashboard 总体计划

日期：2026-05-09

## 摘要

Open Composer 现在已经具备一个可运行的 CLI + 文件仓库型 MVP，但它的能力仍停留在单标的 OHLCV、少量技术指标、简单回测和 paper 订单的阶段。下一步不能把 TradingView 当成所有策略的主运行时，也不能把 Dashboard 做成第二个“真相源”。更稳妥的方向是：

```text
StrategySpec 作为策略源头
  -> Python 研究/回测/扫描引擎作为主语义
  -> Dashboard 作为可视化控制平面和观察平面
  -> TradingView 只承载可兼容子集
  -> Alpaca Paper 只承载受控执行
  -> LLM 只产生结构化、可回放的研究/复核产物
```

本计划把“能力补全”与“Dashboard”放在同一个体系里，因为 Dashboard 不是额外的花哨界面，而是未来策略管理、版本管理、实盘监控、LLM 复核和策略编排的操作面。

## 研究依据

下面这些产品、项目和论文给出了本计划的边界和参照：

| 参考 | 主要观察 | 对 Open Composer 的启发 |
|---|---|---|
| TradingView Pine strategies | 策略脚本运行在 broker emulator 中，适合做策略测试和图表观察，但不是全量量化运行时。 | Pine 只能作为“兼容子集导出”，不能承载全部策略语义。 |
| TradingView limitations | Pine 在请求数量、图形数量、订单数量和历史数据方面都有约束。 | Dashboard 不应依赖 Pine 覆盖所有复杂因子。 |
| Alpaca Trading API | Alpaca 是执行层和数据层，支持 Paper Trading 和下单。 | 执行必须由 Open Composer 控制，不能把 Alpaca 当策略研究平台。 |
| QuantConnect LEAN | 研究、回测、实盘共享一套引擎思想，并有现实模型、交易对象和组合层。 | 要把“研究”和“执行”分层，同时保留一致的语义。 |
| NautilusTrader | 强调事件驱动、回测/沙盒/实盘同构。 | 策略引擎应支持事件流和订单生命周期，而不只是信号布尔值。 |
| vectorbt / QuantRocket | 强项是向量化研究、参数扫描、多策略和组合层回测。 | 高级因子和横截面策略需要独立的研究引擎，而不是只靠单条表达式。 |
| Freqtrade freqUI / Hummingbot Dashboard | 现成产品已经证明：策略列表、版本、实例、回测、运行监控、停止/启动控制都需要一个统一操作界面。 | Dashboard 应该是“策略库 + 运行中心 + 审计中心”，而不是单纯图表页。 |
| OpenAlgo / Composer | 可视化策略构建、Webhook、策略管理、组合/权重/过滤器是成熟产品常见形态。 | 组合策略和扫描策略应当作为一等对象存在。 |
| Qlib / PyBroker / ML4T / LLM 论文 | 机器学习策略需要数据集、特征、训练、walk-forward、预测存储和复现实验。 | 量化 + LLM 不能只靠 prompt；必须有结构化数据层和版本层。 |

## 现状判断

当前仓库已经有这些能力：

- `StrategySpec` YAML 作为策略源头；
- Python 回测、扫描、信号日志、报告、journal；
- Pine 导出；
- Alpaca data / Alpaca Paper；
- capability registry 与 event/news/macro 适配；
- `draft / approved / active / retired` 生命周期；
- LLM review card 的结构化输出。

但现在还缺这些关键能力：

- 复杂因子和更完整的技术指标目录；
- 横截面、组合、排序、调仓类策略；
- immutability 的版本库；
- 可视化 Dashboard；
- 实盘/模拟盘的集中监控和操作；
- LLM 策略在界面中的分层展示；
- 统一的可回放操作审计。

## 设计原则

1. `StrategySpec` 仍然是源头，但它要升级成“可版本化的策略对象”，而不是只有 entry/exit 文本。
2. Dashboard 只能读取和展示派生状态，不能自己发明一套独立真相。
3. 所有写操作必须通过明确的命令和审计记录，不能在 UI 里偷偷改状态。
4. 任何会影响交易的 LLM 输出都必须结构化、版本化、可回放。
5. 默认优先本地、离线、文件可见；外部数据和实时服务只能作为扩展。
6. Dashboard 不是 landing page，不做营销式 hero，不做轻飘飘展示页，而是密集、可扫描、可操作的工作台。

## Dashboard 的技术决策

### 第一版 UI 技术栈

- **UI 层：Streamlit**
  - 理由：本项目当前是单用户、本地优先、表格和图表密集型工作流。
  - 参考意义：Hummingbot Dashboard、Freqtrade freqUI 都证明了“策略管理 + 运行监控”可以先从轻量控制面开始。
- **数据层：本地派生目录 + SQLite 目录库**
  - 文件仍是 source of truth。
  - Dashboard 需要一个本地 SQLite 目录库来索引策略、版本、运行、信号、订单、审计事件和 LLM 产物。
  - 这个目录库是可重建的 read model，不是新的真相源。
- **写入层：复用现有 CLI / Python 服务函数**
  - Dashboard 的按钮不直接改业务状态。
  - 它调用现有的 lifecycle / paper runner / review / journal 逻辑。

### 为什么不是先上重型 SPA

- 当前产品是 CLI + 文件优先，不应该先跳到复杂前端栈。
- 先把信息模型和控制面做对，比先堆 React 页面更重要。
- 如果未来需要多用户、权限隔离、远程部署，再把 UI 从 Streamlit 迁移到前后端分离也不迟。

## 核心对象模型

Dashboard 需要识别这些对象：

- `Strategy`：逻辑上的策略名。
- `StrategyVersion`：不可变版本快照，带 hash、父版本、创建时间、来源 session、prompt/model 信息。
- `StrategyRun`：一次回测、扫描、paper cycle 或未来 live cycle。
- `Signal`：一次 entry/exit 事件。
- `Order`：一次实际执行或模拟执行。
- `ContextPacket`：事件、新闻、宏观、LLM review 的上下文包。
- `StrategyGroup`：编排多个子策略或子组合的上层对象。
- `AuditEvent`：dashboard 的启停、审批、激活、暂停、回滚记录。

## Dashboard 信息架构

### 1. 总览页

显示：

- 当前活跃策略数量；
- 已启用的 paper_auto 策略；
- 最近回测结果；
- 最近 signal；
- 最近订单；
- 当前风险告警；
- LLM review 待处理项。

### 2. 策略库

显示每个策略的：

- 名称、版本、生命周期；
- 模型接入分类；
- 风险等级；
- Pine / Python / Alpaca 可用性；
- 数据来源；
- 最近一次回测和 paper 状态；
- 标签和策略组归属。

### 3. 策略详情页

分成多个 tab：

- 概览；
- 版本历史；
- 回测；
- 扫描；
- signal 日志；
- 订单/纸面执行；
- 事件/新闻/宏观上下文；
- LLM review；
- 审计。

### 4. 版本管理页

显示：

- 当前活跃版本；
- 上一版本与差异；
- 版本 lineage；
- 生成来源（用户、Codex、LLM）；
- 关联的回测和信号；
- 回滚和对比按钮。

### 5. 实盘/模拟盘监控页

显示：

- 现在正在运行的 paper_auto 策略；
- 开仓、平仓、未完成订单；
- 持仓、仓位、暴露度；
- 已实现/未实现盈亏；
- 当日交易次数、当日亏损、心跳；
- 订单延迟、滑点、异常。

### 6. 事件 / 新闻 / 宏观中心

显示：

- 原始事件流；
- 过滤后的事件；
- 由事件转成的因子或标签；
- 与某个策略或策略组相关的上下文；
- 最近一次扫描调用链。

### 7. LLM 中心

分三类展示：

1. Review 类：LLM 只做最后审查。
2. 扫描机会类：LLM 把事件/新闻/宏观转成结构化特征。
3. 组合策略类：LLM 或规则引擎决定启用哪组策略、哪个频率、哪种风险偏好。

### 8. 策略组 / 编排器页

这个页不是普通“管理组”的别名，而是**一等执行对象**。

- `策略组`：负责子策略启用、资本分配、频率切换、组合筛选。
- `管理组`：只是运营视角的分组，例如 owner、环境、风险、资产类别。

结论：

- 组合策略类应该放进 `策略组 / 编排器`，不是只放在“普通策略管理”里。
- 但它也必须出现在总览和管理页里，便于监控和审批。

### 9. 审计 / 权限页

显示：

- 谁在什么时间启用了什么；
- 谁批准了哪个版本；
- 谁触发了 paper_auto；
- 哪些操作失败了；
- 哪些操作被风险规则拦截。

## 策略分类体系

### 按模型接入分类

| 分类 | 定义 | Dashboard 展示 |
|---|---|---|
| 纯量化策略 | 没有大模型参与交易逻辑。 | 绿色标识，默认只显示量化参数、回测和执行。 |
| 量化 + Review | 大模型只负责最后审核，不改交易语义。 | 显示 review 卡、理由和建议，但不把它当成入场因子。 |
| 量化 + 扫描 | 大模型把事件、新闻、宏观转成因子或标签。 | 独立的上下文页和因子转换链路。 |
| 量化 + 编排器 | 大模型或规则引擎决定使用哪组策略、哪种频率、哪种权重。 | 归入策略组页，并显示子策略树。 |

### 按风险等级分类

| 分类 | 典型特征 | Dashboard 提示 |
|---|---|---|
| 稳健型 | 低杠杆、低换手、单标的、规则简单、数据稳定。 | 默认推荐，展示为低风险。 |
| 中等风险 | 中等换手、较复杂因子、可能有横截面或组合层。 | 需要展示回撤、滑点和成本敏感性。 |
| 高风险 | 高频、强依赖外部数据、策略组编排、预测模型、LLM 介入。 | 必须显示警告、版本、审计和更严格的启用门槛。 |

注意：

- 风险等级要分成**人工声明**和**系统推导**两套。
- 如果两者不一致，Dashboard 必须明确提示冲突。

## 版本管理方案

当前仓库的 `draft / approved / active / retired` 只有生命周期，没有真正的不可变版本史。Dashboard 需要补上这一层。

### 建议的版本模型

- `strategy_id`：逻辑策略 ID，跨版本不变。
- `version_id`：单次版本快照 ID。
- `parent_version_id`：来源版本。
- `content_hash`：内容哈希。
- `created_at`：创建时间。
- `created_by`：用户 / Codex / LLM / 手工。
- `prompt_session_id`：如果由对话生成，要能追溯。
- `model_ref`：如果涉及 LLM，要记录模型与提示模板版本。
- `status`：draft / approved / active / retired。

### 版本规则

1. 任何一次编辑都生成新版本，不覆盖旧版本。
2. `active` 只是一个别名或指针，不是唯一物理文件。
3. 版本 diff 要在 Dashboard 中可视化。
4. 版本回滚必须留下审计事件。
5. 回测、扫描和 paper 记录必须能回链到版本。

### 存储建议

- 仍然保留现有目录结构。
- 额外引入一个本地 SQLite 目录库或 JSONL 索引层。
- 文件系统仍然是主存储，数据库只做索引和查询加速。

## 数据与指标展示

### 基础数据

默认展示：

- 回测结果；
- 最近日志；
- 最新信号；
- 最近的 strategy run；
- 最近的版本。

### 如果接了模拟盘 / paper

增加展示：

- 实盘/模拟盘订单；
- 持仓明细；
- PnL 拆分；
- 实现/未实现盈亏；
- 订单状态变化；
- 策略启停时间；
- 事件驱动的执行延迟。

### 如果未来接到更丰富的数据

可以在详情页补充：

- 市场宽度；
- 波动率；
- 行业暴露；
- 事件/新闻热度；
- 预测分数；
- 因子暴露；
- 组合相关性。

## 实施路线

### Phase 0：知识库和目录库

- 维护 `knowledge/` 下的研究知识库。
- 建立本地 dashboard catalog（SQLite 或可重建索引）。
- 把策略、版本、run、signal、order、LLM review、audit 统一索引起来。

### Phase 1：只读 Dashboard

- 策略库列表；
- 策略详情；
- 版本历史；
- 回测与扫描结果；
- 信号和报告；
- 事件/新闻/宏观上下文。

### Phase 2：版本管理

- 新版本写入；
- diff；
- 回滚；
- tag；
- 版本比较；
- 关联运行历史。

### Phase 3：模拟盘监控与管理

- 当前 active 的 paper_auto 策略；
- 订单和持仓监控；
- 启用 / 停用；
- 手动确认；
- 审计日志；
- 与 CLI 安全门一致。

### Phase 4：LLM 工作区

- Review 页面；
- 扫描机会页面；
- prompt / model / 版本记录；
- 结构化输出回放；
- 事件转因子链路。

### Phase 5：策略组和组合管理

- 子策略树；
- 资本分配；
- 频率层级；
- 市场状态到策略组的映射；
- group-level 风险控制。

### Phase 6：高级量化能力

- 因子库扩展；
- 横截面策略；
- walk-forward；
- 多资产组合；
- 更强的执行和成本模型。

## 验收标准

Dashboard 的第一版完成时，应满足：

1. 能列出所有策略、版本和标签。
2. 能查看某个策略的回测、信号、报告和版本差异。
3. 能显示当前 active 的 paper_auto 策略。
4. 能显示 paper 订单、持仓和 PnL。
5. 能查看事件、新闻、宏观和 LLM review 产物。
6. 能以审计方式启用/停用 paper 策略。
7. 能区分纯量化、量化 + Review、量化 + 扫描、量化 + 编排器。
8. 能区分稳健型、中等风险、高风险。
9. 无需外部凭证也能浏览本地样例数据。
10. 不会把 Dashboard 变成另一个新的真相源。

## 默认假设

- 实盘真钱交易继续不在本 MVP 范围。
- Dashboard 先面向单用户、本地运行、文件优先。
- 远程管理只对 paper_auto 且 active 的策略开放。
- 所有写操作都必须有审计记录。
- LLM 相关页面只展示结构化产物，不直接执行未审计逻辑。
