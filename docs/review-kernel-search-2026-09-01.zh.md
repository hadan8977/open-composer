## 0. 结论先说

用户的怀疑是对的。本轮引入了 **6 个方法论缺陷**，其中 4 个会**放松门槛或高估成绩**——
也就是危险的那个方向。全部已修，但**根因值得单独记下来**：

> **反复出现的错误模式：另起炉灶造新机制，而不先查仓库已有的实现。**

`campaign.py` 早有有效 N 的五道防线，`router_common.py` 早有按折重选参数，
`optimizers/` 早有搜索包。kernel 三次绕开了它们，三次都重新引入了那些防线本来挡住的问题。

## 1. 已修复的缺陷

### 1.1 固定参数取代按折重选（用户发现）

kernel 在 2016-2021 上选定**一组**参数，拿去 2022-2026 跑。
而 `router_common.walk_forward_router:465` **一直是每折重选**的。

两个后果：选择环节永远看不到近期 regime；验证的对象不是实际会部署的东西
（实际部署的是"定期重新优化的流程"）。

修复：`kernel/nested_walk_forward.py`，恢复按折重选，**同时保留旧实现缺的
purge+embargo**（`router_common` 的训练期与测试期直接相接）。

实测价值：真实 SIP 日线上，各折选出的 `lookback` 是 210/110/110/130/130，
churn 0.50。**参数是会动的**——固定设计只会报一个数，把这件事藏起来。

### 1.2 DSR 的有效 N 被做小（放松方向）

`layered_search` 只对**存活的精英**聚类，并按该数收 DSR 的费：
60 个候选筛成 5 个、聚成 3 类，就按 3 次试验计价。

`campaign.py:_effective_trial_clustering_blockers` 的 docstring 逐字点名禁止这件事
（"clustering a hand-picked subset"）。**这个缺陷我在 P1a 计划评审时识别过、
在 campaign 路径里修过，然后在 kernel 路径里又犯了一遍。**

修复：聚类**全部已评估候选**并取较大者，只可能收紧。参考运行的试验计数 3 → 6。

### 1.3 选择层看到的是改名后的 OOS（执行代理自查发现）

`Candidate.development_fold_returns` 是把拼接 OOS 流按各折**测试窗口**切片得到的——
展平后与 `oos_return_stream` **逐元素相同（1240/1240）**。
所以"Layer 1/2 只能读它"只是类型层面的隔离，**选择实际上在 OOS 上做**。

字段名本身就是成因。修复：改名为 `oos_fold_returns`（它一直是这个），
新增真正的 `development_returns` = **第一个测试窗口之前**那段，
`expand_mechanism` 在两者有任何日期交集时直接报错。

注意：**逐折训练窗口是错误的替代方案**——锚定扩展窗口下 fold5 的训练期包含
fold1-4 的测试年，实测重叠 1039 天。

### 1.4 未来函数检测器有探针盲区（对抗测试发现）

`assert_causal_transform` 原本固定探测 `[40%, 90%]` 区间。
用**绝对日期锚定**、落在最后 10% 的泄露可以完全穿过——**把探针数加到 40 个也没用**，
因为多出来的探针落在同一个窗口里。盲区正好是最近的数据，也是意外泄露最常发生的地方。

修复：探针范围改为从变换自身预热期末尾到"仍有未来可截断"的最后一个位置。
修复后头部/尾部泄露、居中均值、全样本 z-score 全部拦截，
因果滞后均值 / 因果 EWM / 滚动 std 无误报。

### 1.5 审计指标口径矛盾

报告并排写 `raw_candidate_count: 65` 和 `breadth_ratio: 0.5`，
但 0.5 的分母是 6 个精英，不是 65。照字面读会算出 32 个有效试验，实际是 3 个。
`breadth_ratio` 的**唯一用途就是审计虚假宽度**。

修复：两个分母都明确命名（`breadth_ratio` / `breadth_ratio_vs_discovery`）。

### 1.6 硬编码门槛绕过预注册

`campaign.py` 的阈值是**哈希封存合同的字段**，`mechanism_eval.py` 把一组数字写死在
module dict 里。任何人看到裁定后都能改它。

已做：裁定携带 `gates_provenance`，`MIN_DSR_STREAM_ROWS` 改为从 campaign 导入（消除双份常量）。

随后**已根治**：门槛改为必须来自 git 已提交的合同，见 §3.1。

## 3. 未修复 / 需要决策的问题

### 3.1 kernel 整体在预注册体系之外（**已修复，2026-09-01**）

原问题：campaign 路径的保护是**合同 + 哈希封存 + 五道聚类防线**，
kernel 路径的保护只是**代码里的常量**。§1.2 和 §1.6 都是这个结构性差距的症状。

修复方式参照主流做法——回测过拟合文献（Bailey & López de Prado 的 DSR、
Harvey & Liu 的因子识别协议）的共同要求是**先声明再看结果**；
工程上对应的是 config-as-code + 哈希。这里落地为：

`open_composer/research/kernel/gate_contract.py` 要求门槛来自一个 JSON 文件，且：
- 必须**被 git 跟踪**；
- 必须**没有未提交的改动**；
- 裁定记录该文件的 **git blob SHA-1 与内容 SHA-256**。

看到结果之后改阈值，要么在加载时因工作区脏被拒，要么留下一条可审查的 commit diff。
这挡不住蓄意作弊（没有任何机制能），但**让它必须留下痕迹**——预注册在别处买到的也正是这个。

新增 `CandidateVerdict.promotion_eligible`：**通过全部门槛是必要不充分条件**，
阈值非预注册时恒为 `False`。实测判别性：

```
同一候选、同样数值、三种来源:
  默认门槛          all_gates_pass=True  promotion_eligible=False
  预注册合同        all_gates_pass=True  promotion_eligible=True
  裸 dict(同样数值)  all_gates_pass=True  promotion_eligible=False
```

**把同样的数字内联传进去拿不到晋级资格。** 合同：
`config/promotion/kernel-paper-tier-gates.json`（先于读取它的代码单独提交，
阈值沿用 Work Item A 的重校准值，未做任何改动）。

### 3.2 抓取续传有静默数据缺口的隐患

`BATCH_SIZE` 中途从 40 改成 12，续传只认分片号：

```
整年分片 316（旧run最后）: VSS .. VUSE      <- 字母表 94%
月分片   317（新run第一）: EP.PRC .. EPM    <- 字母表 28%
```

同一个分片号指向完全不同的标的。实测本次**没有丢数据**——新编号起点恰好更靠前，
盖住了旧范围。**但这是运气。** 批大小往大改就是静默缺口。

建议：完成标记里记录 `BATCH_SIZE` 与宇宙大小，续传时不一致则拒绝。

### 3.3 GP 的结构演化仍是全局的

`expression_tree_search` 在开发分区（2016-2021）上演化出精英池，
之后只有"在池子里选哪一个"是逐折的。**表达式的结构仍冻结在 2016-2021 的数据上**——
就是 §1.1 的问题上移了一层。无泄露（演化从未见过任何测试窗口），但适应性受限。

代价：每折重新演化是 5 倍算力。这是权衡，不是缺陷，但必须记录。

### 3.4 "模仿现金"的退化候选在共享质量函数里仍未防住

Layer 1 的 `development_quality` 用裸夏普，这会**结构性偏好**近似"一直持有现金"的候选。
P2b 在自己的准入闸门修掉了，**但 `development_quality` 本身没改，P2a 路径仍暴露**。

### 3.5 `_qqq_capture_gate_passes` 的免费通行

与 QQQ 相关性 ≤0.3 时，两个 capture 门槛直接通过。理由站得住（不相关时捕获率没有意义），
但后果是**噪声策略白拿 8 个门槛里的 2 个**。不足以单独通过（另外 6 个还在）。

**归属澄清**：来自更早的 `a4a5b07`（Work Item A3/A4），**不是本轮引入**。

### 3.6 归置与文档
- `parameter_search.py` 放在 `kernel/`，而仓库已有 `research/optimizers/` 包。
- `spec.data.source` 是 `Literal["sample","alpaca","longbridge"]` 且在禁改文件里，

## 5. 给下一轮的硬规则

1. **动手写新机制前，先在仓库里搜同名/同义的既有实现。** 本轮 3 次教训都来自跳过这一步。
2. **任何改动都要问"方向是收紧还是放松"**，放松方向的改动需要显式论证。
3. **防护必须证明是活的**——注入一个它该拦的东西，看它拦不拦。
   `rejected_lookahead_count: 0` 单独看无法区分"没有泄露"和"防护是死的"。
4. **代理报告的每个数字都要与产物核对**（§3.7）。
5. **命名即契约**：`development_fold_returns` 里装 OOS 数据，是 §1.3 的直接成因。
