# 从机主反复纠错到系统主动发现问题

本次针对研究系统与方法维护，不是新经济实验。采用已保存 pStack 0.15.21 的 correct 方法，并参考 recall、reflect 的多视角与 attack-the-premise/fix-root-causes 原则。未另占用研究槽位执行 reflect 的三代理加综合代理流程，也未宣称完成独立模型行为 A/B。

## 根因判断

1. **前提错误被层层继承。** Root 把实验对象、成本、时间范围写进 brief，执行和审查主要检查是否忠实执行，缺少先问“即使全部通过，是否回答了机主的收益问题”。因此旧样本、错误执行时钟、压力成本都可能被严谨地执行下去。独立方法审计已给出真实反例。
2. **局部完成替代了母问题推进。** 实施、来源或小审查完成后就交回；真实部署门又被提前用于拒绝方法研究。完整 owner 的接续责任与何时挑战原方案没有落实到每次实际派工。
3. **规范文件与真实入口脱节。** 已有角色 prompt，但 Root 仍可手写短派工；更新文档不保证新会话读取。动态状态还复制在 schedule prompt 内，形成多个互相冲突的“当前状态”。
4. **完成信号不代表业务结果。** 调度 succeeded、代理 finished、测试通过都有各自含义，不能替代报告正文、实际研究结果或成本后经济贡献。
5. **汇报本身继承旧尺度。** 现行模板保留 ETF 特有门槛，并把特定结果文件不存在与全部绩效 N/A 混同，可能掩盖有价值的方法结果或夸大负结论。
6. **改进缺少行为验收。** 昨天确实做过预算、设备与证据工程修复，但另外准备的八个判断案例没有实际执行，不能据此声称研究判断已改善。仅追加“更主动”不能关闭这类问题。

## 本次已落地的最小修正

- `scripts/research_task_prompt.py` 从当前角色配置、实际角色 prompt 和现有完整 brief 组装派工，输出精确来源绑定；新任务及接续使用这一入口。AGENTS、CLAUDE、Root/执行 prompt 已接入。真实渲染的接续已发送 Martin、HF、DLSA 三位现有 owner，不新开代理，不打断原生计算。
- 科学审查先独立重建机主要作的决定，再挑战实验前提与替代解释，最后检查实现与门。执行者发现重要错位可主动发出一次决定事件，不等机主或耗尽预算；普通修复继续由完整 owner 完成。区分当前科学结论的缺口、后续部署依赖和可选改善。
- 研究模板按各冻结合同读取标准；近期应用、作者复现、压力情景、真实部署分别解释。20bp 旧晋级门保持原适用范围，不能当作所有研究的实际交易成本。接受的其他结果文件可以报告方法结果，不因 paper 未就绪一律写 N/A。
- 修正三条实际报告 schedule：只保留任务入口，动态许可读权威文件，方法读现行 prompt；不再内嵌“当前报告仍暂停”。保留全部 cadence、model、mode、status 和既有投递路线。
- 在现有 `owner_report.py` 增加只读 `health <event_id>`：核对正文、状态及已有 hash，明确“正文存在”和“已发布/已读”不同。现有正常报告轮顺带核对上一到期报告，发现同一事故只通知一次，不新建定时器或 Astra 值守。

## 实际发现与验证

控制文件已于 10 月 13 日恢复报告，但三条实际调度 prompt 仍写“当前报告仍暂停”。核到 18 条运行记录（16 条整轮、1 条日报作者、1 条日报/周报触发）因此退出，调度器仍记 succeeded。16 条整轮包含一次重复时间记录，不冒充 16 个不同窗口；这也不证明邮件 cron 没有发送其数据后备版本。

三条 prompt 已更新并回读，调度配置不变。真实命令 `owner_report.py health round-20261014T160000Z` 退出 1，识别为 missing_business_result。下一次正常整轮计划在 2026-10-14 18:05 UTC；届时正文生成与发布尚待实际验收，当前不能报“全流程已恢复”。

14 个不同定向测试通过：5 个派工组装、6 个报告业务结果检查、3 个原报告发送回归；重复运行不增加测试数。scoped Ruff 与 agent-parity 通过。测试针对漏读当前 prompt、假完成、缺正文、hash 漂移及真实暂停等具体失败，不代表模型科学判断正确。

## 后续如何判断这次是否有效

直接复用三条研究任务的下一次正常结果与正常报告，不另造评估工程。看执行者能否在扩大投入前主动发现决定性前提错位，审查是否指出最强替代解释，负结果是否得到正确接续，以及报告是否真的产生并区分方法/经济/部署结论。Root 对这些判断负责，不能再把机主当最后一道常态质检。

本次未证明收益、效率或 token 消耗已改善，亦不能保证以后零错误。旧八案例仍未做独立模型对照；不把规则、代码和测试数量当成行为改进。最关键的验收是：在机主再次指出之前，系统是否发现并解决真实问题，同时让研究继续产出有用证据。
