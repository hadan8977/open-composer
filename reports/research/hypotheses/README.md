# 假设卡（Hypothesis cards）

2026-09-21：日常有界研究已受用户委托，不再逐卡等审批；仍须先联网查方向并过机器检查。最新目标、预算与资金权限边界见 `docs/research-mission.zh.md`。看板里的旧 proposed/approved 标签只是历史记录，恢复前先看后续否定证据，不能按旧泳道盲跑。

每张卡是一次可被推翻的实验。状态流转：proposed → approved（你批准或按 2026-09-16 的委托默认批准）→ running → done（写复盘卡到 `../lessons/`）。
规则（来自 `docs/proposal-research-loop-redesign-2026-09-15.zh.md` 2.4/2.5）：
- 方法一栏必须引用 `reports/research/intel/` 简报或有 URL 的一手来源；没有出处的卡不合格。
  （2026-09-24 更正：`knowledge/digest/` 只覆盖 2026-09-11 前的 Step 11/13 网格实验族，之后的卡从未写入它，
  已核实现有 19+ 张卡无一引用它；实际出处一直是下面"情报节"要求的 `reports/research/intel/` 简报和直接文献/URL，
  这里改成写实际做法。）
- 必须写"什么结果算否定"和占位设计；缺一不能批。
- 每张卡只改一处（一个数据层、一个目标或一个模块）。
- 试验计入 `trial-families.json` 的假设族；DSR 用族的累计计数算。
- 评分函数和门槛定义只有用户能改。
- 复盘必须报 SPY / MTUM / SPMO / 同波动超额 / 占位五个数。

## 情报节是必填的（2026-09-18 起）

每张新卡在"设计"之前必须有一节 **情报**，四个问题各一行，引用 `reports/research/intel/` 下的简报：

1. 来源最后更新时间、基准数字的市场与时间段（新不新）；
2. 第三方复现状况（没有就写"只有作者自己说"）；
3. 有没有人已经做出来并分享（净值曲线、对账单、可运行代码 + licence）；
4. 在本机（3.9 GB 内存 / 2 核 / 无 GPU / 无 torch）与本地数据上能不能跑，不能跑的部分写清楚。

再加一行 **最便宜的决定性测试**：如果这个假设是错的，哪个最小的测试最快把它否掉，预计跑多久。
没有情报节的卡不许开始跑。理由见 `reports/research/intel/README.md`。

## Cockpit 怎么读这些卡（Step 18 T4，2026-09-19）

`open_composer/cockpit/data/hypotheses.py` 会把这个目录下每张 `*.md`（`README.md` 本身除外）解析成一张卡，
放进看板的一个泳道：`preregistered` / `running` / `shipped` / `refuted` / `on hold` / `unclassified`。解析是**容错**的——
现有 19 张卡的格式并不统一（有的把 `状态：` 写成裸行，有的写成 `- 状态：` 项目符号；`层`/`数据层`/`执行脚本`/
`产出目录`/`产出`/`上一环`/`教训` 这些字段有的在标题正下方，有的散在正文的"成本与执行"一节里），
解析器按关键词容忍这些差异，但**任何一张卡都不会被静默丢弃**：解析不确定就进 `unclassified` 泳道，并带上原始状态文本和
不能分类的原因。

同样地，研究血统图（屏 2）默认只能靠两种证据连线：卡片自己写的 `上一环：` 字段（实线，强证据）和正文里出现的其它
卡号（虚线，弱证据——只是"提到"，不代表"承接"）。截至 2026-09-19，19 张卡里只有 1 张写了 `上一环`，
所以图上大多数连线目前是弱证据的虚线；这是语料的事实，不是解析器的缺陷。**新卡请务必写 `上一环：`**，
这样这张卡在血统图上就会立刻多一条实线，而不用等 cockpit 去正文里猜。

### 可选的 YAML front-matter（面向未来的新卡，不要往现有 19 张卡里补）

新卡可以在标题行之前加一段 `---` 包裹的 YAML front-matter，把状态/泳道/上一环/预注册判定标准写成结构化字段。
写了 front-matter 的字段会被 cockpit **优先**采用（跳过关键词猜测）；没写的字段仍然按老办法从正文解析。
不要求所有字段都填，也不要求现有卡片补写这段——这纯粹是"如果你想让新卡更精确，可以这样写"。

```yaml
---
card_id: H-20260920-01
status: 已执行，通过，上线
lane: shipped
previous: H-20260919-02
criteria:
  - name: select_sharpe_vs_incumbent
    threshold: 0
    direction: ">"
  - name: holdout_sharpe
    threshold: 1.0
    direction: ">="
---
# H-20260920-01 卡片标题……
```

字段说明：

- `card_id`：应该和标题行里的卡号一致；不一致时 cockpit 会记一条 parse warning，但仍以标题行的卡号为准。
- `status`：优先于正文里扫到的 `状态：` 行。
- `lane`：必须是六个泳道名之一（`preregistered`/`running`/`shipped`/`refuted`/`on hold`/`unclassified`），写了就直接采用，
  不再走关键词猜测；写了一个不认识的值会退回关键词猜测并记一条 warning。
- `previous`：等价于正文里的 `上一环：`，会成为血统图上的一条实线。
- `criteria`：每条判定标准的 `name`/`threshold`/`direction`。**这只是把预注册标准列出来**，cockpit
  不会自动把它和某个 `summary.json` 里的数字配对判定通过/不通过——那需要一个可靠的、按名字精确匹配的映射，
  没有这个映射就去猜数字和标准的对应关系，等于编造一张本不存在的判定表。卡片详情页会把这些标准原样列出，
  和 `summary.json` 里的数字并排放，但两边的比较仍然标注"未结构化（人工对照）"，由人来看。
